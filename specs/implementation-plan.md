- [x] **Task 2.2:** Implement Finite State Machine (`IDLE`, `ACTIVE_SET`, `EDIT_SET`, `RESTING`). Implemented as a standalone `WorkoutStateMachine` (not yet wired into `SetSyncDelegate`/`SetSyncView`, which is Task 2.4's scope) covering exactly the transitions in `specs/modules/01-garmin-app.md` §3: START/STOP cycles `IDLE → RESTING → ACTIVE_SET → EDIT_SET → RESTING`; `BACK (Hold)` only transitions `RESTING → IDLE`; `UP/DOWN` never changes state (`canAdjustSet()` invariant, true only in `EDIT_SET`). Any trigger undefined for the current state is a no-op — no implicit/undefined transitions. Accelerometer start/stop (Task 2.3), vibration/SET_COMPLETED enqueueing (Task 2.5), and physical button wiring (Task 2.4) are intentionally out of scope here.
- [x] **Task 2.3:** Implement accelerometer sampling (25 Hz) and SMA peak-detection filter. `RepDetector` implements `specs/modules/01-garmin-app.md` §2 exactly: 5-sample circular-buffer SMA, then hysteresis peak detection (1.2g dynamic threshold → 800 ms refractory lockout → 0.9g valley confirmation before re-arming). `AccelerometerSensor` wraps `Sensor.registerSensorDataListener` at `{:period => 1, :accelerometer => {:enabled => true, :sampleRate => 25, :includeTimestamps => true}}` (verified against the installed Connect IQ 9.2.0 SDK's own `PitchCounter` sample and `AccelerometerData` API docs, since values are in milli-G — divided by 1000 before computing `a(t) = sqrt(x²+y²+z²)`), feeding each raw sample + its real timestamp to `RepDetector`. **Manifest change:** compiling surfaced `Permission 'Sensor' required for Toybox.Sensor...`, so `<iq:uses-permission id="Sensor"/>` was added to `garmin/manifest.xml` (alongside the existing `Communications` permission). - [x] **Task 2.4:** UI Views & Input Handling. Wires `WorkoutStateMachine`, `RepDetector` and `AccelerometerSensor` into `SetSyncView` (orchestrator) and `SetSyncDelegate` (input), and renders a distinct screen per state per `specs/modules/01-garmin-app.md` §1: `IDLE` (start prompt), `RESTING` (last-set summary + rest elapsed mm:ss), `ACTIVE_SET` (live rep count + set duration mm:ss), `EDIT_SET` (editable reps/weight). Physical buttons per §3: `KEY_START` → `onStartStopPressed()` (drives the FSM; on `ACTIVE_SET → EDIT_SET` also stops the sensor and vibrates per the table's "vibra" note, guarded by `Attention has :vibrate`; on `RESTING → ACTIVE_SET` resets `RepDetector` and starts the sensor); `KEY_UP`/`KEY_DOWN` → adjust the focused EDIT_SET field (+/-1 rep or +/-1.0 kg, only while `canAdjustSet()`); `KEY_ESC` timed via `onKeyPressed`/`onKeyReleased` (§3 gives no exact hold duration, so a conventional 1000 ms threshold is used) to distinguish `BACK (Hold)` (`RESTING → IDLE`) from a short press. **EDIT_SET focus-toggle decision** (§3 lists UP/DOWN adjusting "reps or weight" but no button to pick which — resolved with you before coding): dual control — a short BACK press (unbound otherwise in `EDIT_SET`) toggles focus between REPS/WEIGHT, and, since the fr165 is touch-capable, tapping the REPS or WEIGHT half of the screen (`onTap` + `editSetFieldAt`) selects it directly; the active field is highlighted (`COLOR_YELLOW`). Confirming a set (`EDIT_SET → RESTING`) only snapshots `_lastSetReps`/`_lastSetWeightKg` for the RESTING summary — building/sending the `SET_COMPLETED` payload stays Task 2.5's scope. `DEFAULT_WEIGHT_KG = 20.0` is used to pre-populate the first set's weight (not specified by spec; a reasonable starting default). Not verified interactively (headless environment, no simulator button presses) — only compiled. **Post-review fix (simulator testing found buttons unresponsive + IDLE text clipped on the round bezel):** `SetSyncDelegate` now also implements the behavior-level dispatch path (`onSelect()`, `onPreviousPage()`, `onNextPage()`) alongside raw `onKey()`, since devices vary in whether START/STOP surfaces as `KEY_START`, `KEY_ENTER`, or only the `onSelect()` behavior callback — `onKey()` now also accepts `KEY_ENTER`. All of these still funnel into the same `SetSyncView` methods, which already called `WatchUi.requestUpdate()` on every mutation, so no double-firing/redraw risk. `drawIdle()` was split into three shorter lines closer to vertical center (`FONT_MEDIUM`/`FONT_SMALL`/`FONT_XTINY`) so no line clips the round 390x390 bezel. **Second post-review round (further simulator testing):** (1) **Rest-timer start moved earlier:** `_restStartMs` is now set at `ACTIVE_SET → EDIT_SET` (the instant the set physically ends) instead of at `EDIT_SET → RESTING`, so time spent adjusting reps/weight counts as rest — per `specs/01-system-spec.md` §1.2/§2.1, this also means `restSec` in the `SET_COMPLETED` payload (built from `_lastRestDurationSec`, still captured at the *next* `RESTING → ACTIVE_SET`) now includes that editing time, since the rest clock has already been running since the previous set ended. (2) **BACK crash fixed:** `SetSyncDelegate` was relying only on `onKeyPressed`/`onKeyReleased` for BACK, but the default `BehaviorDelegate.onBack()` was still independently dispatched and called `WatchUi.popView()`, crashing this single-screen device app (simulator blue-triangle reset) — now `onBack()` is overridden to just `return true` and consume the event. `_backPressedAtMs` is now `Number?` (null until a real `KEY_ESC` down is observed) so `onKeyReleased` can't compute a bogus held-duration from an unmatched release. (3) **Bottom-hint clipping on the round bezel:** `EDIT_SET`'s single 48-character hint line is now three short lines (`"UP/DOWN: adjust"` / `"BACK/tap: switch field"` / `"START: confirm"`) raised to `height-80/-60/-40`, with the REPS/WEIGHT blocks compacted to make room; `RESTING`'s hint moved from `height-40` to `height-55`. (4) **IDLE overlap:** `drawIdle()` now stacks "SetSync"/"START"/"to begin workout" using `dc.getFontHeight(font)` for each line's actual height instead of fixed guessed offsets, so they can't collide regardless of font metrics. **Third post-review round (EDIT_SET UX refactor, minimalist interface):** the three-line bottom help block is removed entirely — no explanatory text on screen, only the yellow highlight communicates what UP/DOWN will affect. `_editFocus` is now a 3-way cycle `:reps → :weightWhole → :weightDecimal → :reps` (both BACK-short-press and tap advance the same cycle, replacing the old "tap a screen half to select directly" mechanism, which is removed along with `editSetFieldAt()`): `:reps` adjusts `_editReps` by ±1 (`REP_STEP`) as before; `:weightWhole` adjusts `_editWeightKg` by ±1.0 kg (`WEIGHT_WHOLE_STEP_KG`); `:weightDecimal` adjusts it by ±0.5 kg (`WEIGHT_DECIMAL_STEP_KG`), which — since the field is a single `Float` — naturally toggles the tenths between `.0`/`.5` when the value is already on that grid (it always is, since every adjustment is a multiple of 0.5 starting from `DEFAULT_WEIGHT_KG = 20.0`). The weight value is rendered as two independently-colored substrings (`drawWeightValue()`, splitting the formatted `"%.1f"` string on `.` and measuring each part with `dc.getTextWidthInPixels` to keep them visually contiguous and centered) so only the whole-number digits highlight yellow under `:weightWhole` and only the decimal digits (`.0`/`.5`) highlight under `:weightDecimal` — the clear "indicación de décimas" the correction asked for, without adding any label text. `drawEditSet()` now spreads REPS (top-of-center) and WEIGHT (below-center) across the space the removed hint block freed, so the REPS value and WEIGHT label are no longer adjacent (120px gap instead of being compacted together). **Fourth post-review round (visual polish, sport-Garmin-AMOLED aesthetic):** RESTING's `"N reps @ W kg"` summary is replaced with a structured, `@`-free `"N reps  •  W kg"` line where the numbers are white and the `reps`/`•`/`kg` labels are `Graphics.COLOR_LT_GRAY` (built with a new generic `drawSegments()` helper — a list of `[text, color]` pairs laid out as one visually contiguous centered line; `drawWeightValue()` in `EDIT_SET` was refactored onto the same helper, removing duplicate width-measuring logic). Visual hierarchy: `RESTING`'s `00:XX` timer and `ACTIVE_SET`'s rep count are now each drawn in `Graphics.FONT_NUMBER_HOT` (the largest numeric font) as the unmistakable focal point of their screen, with every other element on that screen demoted to a smaller font. Consistent per-state accent colors on each screen's header text: `IDLE` white/`COLOR_LT_GRAY` (subtle, no state color), `ACTIVE_SET` `COLOR_GREEN` (also applied to the rep-count itself, signaling live activity), `RESTING` `COLOR_BLUE` (recovery), `EDIT_SET` inactive fields `COLOR_LT_GRAY` / focused field `COLOR_YELLOW` (unchanged, already matched the ask). A new `drawDivider(dc, y)` helper draws a `Graphics.COLOR_DK_GRAY` horizontal line between header/content/footer on every screen; unlike the earlier text-clipping fixes (which used guessed pixel margins), its half-width is *computed* from the round 390x390 bezel's actual circle geometry (`sqrt(radius² − dy²)` minus a fixed margin) at whatever `y` it's asked to draw, so it is geometrically guaranteed never to touch the curved edge rather than relying on another guessed constant. Footers (`"START to begin set"`, `"STOP to finish set"`) stay `Graphics.FONT_XTINY`/`COLOR_LT_GRAY`, small and muted so they don't compete with the headline metric; `EDIT_SET` still has no footer at all, per the third round's minimalist decision, which stands. **Fifth post-review round (divider/text overlap + end-of-session confirmation):** the fourth round's dividers used guessed pixel offsets (`62`, `height - 70`) independent of the actual header/footer text — `drawDivider(dc, 62)` could land inside "RESTING"/"ACTIVE SET" and the `height/2 - 5` middle divider in `EDIT_SET` could land inside the REPS value, depending on real font metrics. Fixed by deriving every divider `y` from `dc.getFontHeight(font)` of the adjacent text plus a fixed `DIVIDER_PADDING = 10`: header dividers now sit at `headerY + getFontHeight(headerFont) + 10`, footer dividers at `footerY - 10`. `EDIT_SET` goes further and stacks its *entire* layout cumulatively (`y += getFontHeight(...) + padding` after each element, title → divider → REPS label → REPS value → divider → WEIGHT label → WEIGHT value) instead of fixed `height/2 ± N` offsets, so no divider (or any element) can ever land on top of another regardless of font metrics — the same fix applied to `RESTING` and `ACTIVE_SET`'s header/footer dividers, since `ACTIVE_SET` shared the exact layout pattern already found broken in `RESTING` (same `28`/`62`/`height-70` numbers) even though it wasn't explicitly reported. **End-of-session confirmed:** `BACK_HOLD_THRESHOLD_MS` raised `1000ms → 1500ms` (steadier hold-to-confirm, less prone to an accidental firm tap). Added an explicit (previously-missing) `RESTING → IDLE` branch in `handleTransition()` documenting that any `SET_COMPLETED` still queued in `CommunicationsService` and not yet `SYNC_ACK`'d is intentionally left alone: the queue and its 10s retry timer live on `SetSyncView`'s single `CommunicationsService` instance, independent of FSM state, so they keep retrying in the background through and after the `IDLE` transition — nothing pending is dropped when a session ends. **Sixth post-review round (bottom-bezel overflow, RESTING + EDIT_SET):** the fifth round's fix stopped dividers overlapping text, but the *total* accumulated content in `EDIT_SET` (title + 2 dividers + 2×`DIVIDER_PADDING`(10) + label/value pairs) still ran past the bottom of the round bezel, clipping the weight value; `RESTING`'s footer (`height - 52`) also sat too close to the curved edge. - [x] **Task 2.5:** Implement `Toybox.Communications` sender and local FIFO queue for `SET_COMPLETED` payloads. `SetCompletedPayload.build()` constructs the `specs/01-system-spec.md` §2.1 Dictionary with the exact keys (`msgType`, `payload.setId/reps/weightKg/durationSec/restSec/timestamp`), unchanged from the spec's schema per RULES.md §3 invariant-payload rule. `durationSec`/`restSec` are captured at the transitions that actually bound them (`_lastSetDurationSec` at `ACTIVE_SET → EDIT_SET`, `_lastRestDurationSec` at `RESTING → ACTIVE_SET`), then used when `SetSyncView` confirms the set (`EDIT_SET → RESTING`) and calls `CommunicationsService.enqueueSetCompleted(...)`. **Timestamp decision:** `Time.now().value()` is seconds since the Garmin epoch (1989-12-31), not Unix epoch, so a documented fixed offset (`GARMIN_TO_UNIX_EPOCH_OFFSET_SEC = 631065600`) converts it, matching the Unix-timestamp magnitude in the spec's own example; `setId` is that Unix timestamp in ms, stringified. `SyncQueue` is an in-memory (volatile) FIFO — one of the two storage options `specs/modules/01-garmin-app.md` §4 allows — with `enqueue`/`peekFront`/`removeById`/`isEmpty`. `CommunicationsService` sends only the front item via `Communications.transmit()` (never more than one in flight), removes it from the queue only on a real `SYNC_ACK` app message (`registerForPhoneAppMessages`, §2.3) — not merely on `onComplete()`, which per §4 just means the transmit reached the phone's Bluetooth stack — and retries every 10 s (`§4`'s exact interval) while the queue is non-empty and `DeviceSettings.connectionAvailable` is true. **Scope boundary:** this task is explicitly `SET_COMPLETED` only (both in this plan and in your task description); `SESSION_EVENT` (START/STOP) transmission mentioned in the FSM table's Spanish notes is not implemented — flagging this as a known gap rather than silently dropping it, in case a future task should cover it.

## Phase 3: iOS Core & Sync Layer
- [x] **Task 3.1:** Download/link `ConnectIQ.framework` in CI pipeline and configure iOS Info.plist entitlements (Bluetooth & HealthKit). **Distribution mechanism decision** (researched, not guessed): Garmin's official SDK repo (`github.com/garmin/connectiq-companion-app-sdk-ios`) ships `ConnectIQ.xcframework` as a binary target behind a `Package.swift` — i.e. it's consumable as a normal Swift Package. `project.yml` adds it via XcodeGen's `packages:`, pinned to the SDK's latest tagged release (`1.8.0`, current at time of writing) rather than a floating branch, so the CI build always resolves the exact same binary — this is what satisfies `specs/modules/02-ios-core-and-sync.md` §5's "descarga del SDK oficial... desde su repositorio/release oficial" without a hand-rolled curl/unzip step: `xcodebuild`'s own SPM resolution does the "download," reproducibly, from Garmin's official repo. **Info.plist mechanism reverted from `GENERATE_INFOPLIST_FILE` back to `info: properties:`** (both in `specs/modules/02-ios-core-and-sync.md` and against the Task 1.4 canonical rewrite you provided): `GENERATE_INFOPLIST_FILE`'s `INFOPLIST_KEY_*` build-setting mechanism only synthesizes Apple's fixed set of scalar (string/bool) Info.plist values — it cannot express the array/dict-valued keys this task requires (`LSApplicationQueriesSchemes`, `CFBundleURLTypes`, `UIBackgroundModes`), which are mandatory per Garmin's own iOS SDK documentation. `info: properties:` is XcodeGen's only mechanism that supports arbitrary nested plist structures, so it's a technical necessity here, not a stylistic reversal — the scalar keys Task 1.4 needed (`CFBundleDisplayName` etc.) are included in the same block for a single source of truth. **Info.plist/entitlements keys added** (each grounded in Garmin's own iOS SDK documentation/example app at `github.com/garmin/connectiq-companion-app-sdk-ios` and `.../connectiq-companion-app-example-ios`, not guessed): `NSBluetoothAlwaysUsageDescription` + `NSBluetoothPeripheralUsageDescription` (Garmin's docs cite the latter as the one iTunes Connect required historically; the example app ships the former; both included), `UIBackgroundModes: [bluetooth-central]`, `LSApplicationQueriesSchemes: [gcm-ciq]` (required so the app can detect/launch Garmin Connect Mobile), `CFBundleURLTypes` registering a `setsync-ciq` scheme (Garmin's SDK docs: "a string not likely to collide with any other apps" — this scheme is only *declared* here; the matching `[ConnectIQ sharedInstance] initializeWithUrlScheme:...]` call is Task 3.2's code, not this task's plist config) — per `specs/01-system-spec.md` §1/§2, `NSHealthShareUsageDescription` and `NSHealthUpdateUsageDescription` (both requested explicitly; HealthKit access here is read-only per `specs/modules/02-ios-core-and-sync.md` §3, so `NSHealthUpdateUsageDescription` is technically optional for a `toShare: []` authorization request, but included since you asked for it explicitly and it's harmless). `entitlements: properties: com.apple.developer.healthkit: true` added for the HealthKit capability. **Known risk, not a blocker for this task:** Apple has historically restricted the HealthKit entitlement to paid Apple Developer Program accounts — free/personal-team provisioning (the only signing path SideStore/Sideloadly sideloading uses under this project's zero-cost constraint) may or may not be able to actually provision this entitlement at install time; this doesn't affect the unsigned CI build (entitlement provisioning is only checked at code-signing time, which this pipeline explicitly skips), but is worth being aware of before relying on the HealthKit feature (`DashboardView`, Task 3.4) on-device. `.github/workflows/build-ios.yml` gained an explicit `xcodebuild -resolvePackageDependencies` step between `xcodegen generate` and the build, so Swift Package resolution (fetching `ConnectIQ.xcframework` from Garmin's repo) happens as its own visible, diagnosable CI step rather than silently inside the build step.
