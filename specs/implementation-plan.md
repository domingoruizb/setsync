## Post-Launch Fix: SetSync No Aparecía en Ajustes → Salud (Apple Health)

Field-test finding: SetSync never appeared under Ajustes → Privacidad y seguridad → Salud → Acceso y dispositivos at all, and "Guardar en Apple Health" failed immediately every time.

- **[x] Root cause: authorization was only ever requested lazily, dependent on `TodayView` having appeared.** An app is only listed in that Settings screen once it has actually *called* `requestAuthorization` — this was previously only triggered from `TodayView.onAppear`, with no independent guarantee it had run (or run successfully) before `saveWorkout` was ever attempted. - **[x] Precise failure diagnosis, not a generic "failed" flag.** `saveWorkout` explicitly checks `healthStore.authorizationStatus(for: workoutType) == .sharingAuthorized` before attempting the write — share/write authorization status (unlike read) is reliably introspectable, since the app itself is the one creating that data, so there's no privacy reason for HealthKit to hide it. `saveWorkout`'s completion changed from a plain `(Bool) -> Void` to `(Result<Void, SaveWorkoutError>) -> Void`, with `SaveWorkoutError` (`.notAvailable`/`.sessionNotFinished`/`.authorizationDenied`/`.underlying(Error?)`) conforming `LocalizedError` so `SessionDetailView`'s failure alert now shows the *actual* reason (e.g. "SetSync no tiene permiso para escribir en Salud. - **[x] Console logging on every failure path** (`requestAuthorization` at launch, `saveWorkout`'s own re-request, the authorization-status check, and `healthStore.save` itself) — each prints `error.localizedDescription` (or the raw `HKAuthorizationStatus.rawValue` when the failure is "not authorized" rather than an `Error`) via `print(...)`, so a future field-test report can include the exact HealthKit-reported code instead of just "it failed."
- **[x] Info.plist purpose strings verified**, not re-written — `NSHealthShareUsageDescription`/`NSHealthUpdateUsageDescription` were already both present as `String` properties in `ios/project.yml` (corrected to accurate Spanish text in the entry just above this one); confirmed no YAML/XcodeGen structural issue was silently dropping either key from the generated Info.plist.
- **Verification:** same no-local-Swift-toolchain caveat as every iOS task since 3.1; whether SetSync now actually appears in Ajustes → Salud and whether the console logs surface a concrete `HKError` code can only be confirmed on a real device.

## Post-Launch Fix (round 2): Aún Sin Modal de Permisos ni Entrada en Ajustes → Salud

Field-test finding: the fixes above weren't enough — the system permission sheet never appeared at all, and the same failure alert kept showing.

- **[x] Entitlements made explicit and complete.** `ios/project.yml` now also declares `com.apple.developer.healthkit.access: []` alongside `com.apple.developer.healthkit: true` (empty array = no Clinical Health Records access — matches exactly what Xcode's own HealthKit capability toggle generates even when Clinical Records is left unchecked, so nothing generated by hand differs from what a normally-configured Xcode target would have), and an explicit `CODE_SIGN_ENTITLEMENTS: App/Sources/SetSync.entitlements` build setting — redundant with what XcodeGen's `entitlements:.path` already wires up automatically, but made explicit so there's no ambiguity.
- **[x] Flagged, not silently assumed fixed: this project's CI builds the `.ipa` with `CODE_SIGNING_ALLOWED: NO`/`CODE_SIGNING_REQUIRED: NO`, and entitlements are normally embedded into a binary's signature *during* code signing.** An unsigned build may carry no embedded entitlements at all regardless of what `project.yml`/the `.entitlements` file say, and whatever re-signs the `.ipa` at sideload time (Sideloadly, with a free Apple ID) is what would actually need to grant the HealthKit capability in the final on-device provisioning profile. This is outside what a repository-level fix can guarantee — if the new diagnostic logs below show `authorizationStatus` stuck at `.notDetermined` even after `requestAuthorization` completes with no error, that's the concrete signal pointing at this, not at app code.
- **[x] `saveWorkout` no longer skips re-requesting authorization based on the status it read** — it already didn't (the guard order was already: log status → unconditionally call `requestAuthorization` → check status again after), but this is now explicitly commented so it's unambiguous: `.notDetermined` is the *only* status that actually shows the system sheet, and calling `requestAuthorization` when already `.sharingAuthorized`/`.sharingDenied` is a safe no-UI no-op, so there was never a reason to special-case skipping the call.
- **[x] Every HealthKit entry/exit point now logs unconditionally** with a `🩺 [HealthKitService]` prefix (not just on failure): `init` logs `isHealthDataAvailable()`; `requestAuthorization` (launch) logs availability, the workout-share status before and after the request, and the request's own `success`/`error`; `saveWorkout` logs availability, current status, and the session's id/sync-state/endDate at entry, then the post-request status; `performSave` logs immediately before and after `healthStore.save`. A future field-test report can now include the exact `HKAuthorizationStatus` and `Error.localizedDescription` instead of "it failed."
- **[x] `SaveWorkoutError.authorizationNotGranted(HKAuthorizationStatus)` replaces the flat `.authorizationDenied`** — the surfaced message now names the actual status (`"no determinado (el diálogo de permisos nunca se ha mostrado)"` vs. `"denegado"`) via a new `statusDescription(_:)` helper, so `SessionDetailView`'s alert (still just showing `error.localizedDescription`, unchanged) now distinguishes "the permission sheet has never even been shown" (pointing at the entitlements/signing question above) from "the user explicitly said no" (an actual Ajustes fix).
- **[x] Explicit main-queue dispatch** around both `healthStore.requestAuthorization` call sites, as a defensive belt-and-suspenders measure — HealthKit's own API is documented as callable from any thread, and every call site here was already on the main actor (SwiftUI `.task`/button actions), so this isn't expected to be the actual fix, but it directly satisfies this round's explicit ask and costs nothing.
- **Verification:** same no-local-Swift-toolchain caveat as every iOS task since 3.1. Next field test should check the Xcode/Console log for the `🩺` lines specifically — if `isHealthDataAvailable()` is `true` but the workout-share status never leaves `.notDetermined` even after a `success=true` `requestAuthorization` completion, that confirms the entitlement isn't actually active on the installed binary (the CI/sideload signing question above), which no further Swift-side change can fix.

## Post-Launch Pivot: Apple Health Descartado — Exportación a TCX para Strava

Confirmed root cause of the last two rounds' field-test failures: a provisioning profile generated from a free/personal-team Apple ID (this app's actual signing path for sideloading via Sideloadly) never gets the `com.apple.developer.healthkit` entitlement granted by Apple at all — HealthKit access, read or write, was blocked at the OS level on real hardware regardless of any app-side authorization/entitlements/logging fix. The whole HealthKit-write feature (and its diagnostics) was reverted, not just patched further.

- **[x] Full revert of the write path.** `WorkoutSession.isSyncedToHealth` removed; `HealthKitService` reverted to its original read-only shape (`saveWorkout`/`SaveWorkoutError`/`performSave`/`workoutSummary`/the verbose `🩺` diagnostics all deleted, `requestAuthorization` back to requesting only the three read quantity types with an empty `toShare`); `GarminSyncService` reverted to its original single-`modelContext` constructor (no more `healthKitService` dependency, no `saveWorkout` call in its `STOP` handler); `ActiveWorkoutView.finishWorkout()` reverted to not touch HealthKit at all; `RootTabView`'s launch-time `.task { requestAuthorization }` removed per this task's explicit "Limpieza" instruction. `ios/project.yml` reverted to its original entitlements (`com.apple.developer.healthkit: true` only, no `.access`/no explicit `CODE_SIGN_ENTITLEMENTS`) and `NSHealthUpdateUsageDescription` reverted to the original honest "SetSync does not write health data" text, since it no longer does. The pre-existing read-only steps/calories feature (`TodayView`) is left in place — it predates this whole detour and is architecturally unrelated to the write path that was removed — but is flagged in code comments as *possibly* silently non-functional on real hardware for the exact same entitlement reason, worth a look if anyone ever asks "why does Hoy always say 'Sin datos de salud todavía'?"
- **[x] New `TCXExportService`** generates a Training Center Database (TCX) v2 XML string/file for a `WorkoutSession`: `<Activity Sport="Other">` → `<Id>`/`<Lap StartTime>` in UTC ISO 8601 (`ISO8601DateFormatter`, `.withInternetDateTime`, explicit UTC time zone) from `session.startDate`, `<TotalTimeSeconds>` from `endDate - startDate`, a two-`Trackpoint` `<Track>` (start and end, time-only — satisfies parsers, like Strava's, that expect at least one track) and a `<Notes>` summary (per-exercise sets/reps/peso máx./volumen, plus a total-volume line) — element order inside `<Lap>` follows the actual TCX v2 XSD sequence rather than guessing, since getting it right costs nothing. `escapeXML` guards the free-text `Notes` content against breaking the XML if an exercise name or the summary text ever contained `&`/`<`/`>`/quotes. Falls back to `endDate ?? startDate` (a zero-duration lap) rather than crashing if ever called on an unfinished session.
- **[x] `SessionDetailView`'s Apple Health section replaced** with "Exportar para Strava (.tcx)" via a native `ShareLink(item: tcxExportURL, preview:)` — `URL` is `Transferable` out of the box, and for a local file URL `ShareLink` shares the file itself (not a web link), so the system share sheet offers Save to Files/AirDrop/Mail/etc. with no entitlement or third-party dependency of any kind. A caption underneath points to `strava.com/upload/select` from Safari as the direct upload path, per this task's exact wording. Gated the same way the discarded Health section was (hidden with a "termina el entrenamiento" hint while `endDate == nil`) for the same underlying reason: an in-progress session has no real duration yet.
- **Verification:** same no-local-Swift-toolchain caveat as every iOS task since 3.1; whether Strava actually accepts the generated `.tcx` file end-to-end can only be confirmed by an actual upload attempt.
